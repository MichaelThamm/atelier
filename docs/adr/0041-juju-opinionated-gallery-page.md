# ADR-0041: An opinionated Juju page on the generated site

## Status

Superseded by [ADR-0057](0057-single-gallery-page.md) for the split between the
agnostic and provider-specific pages. Its credential and channel defaults were
superseded earlier by [ADR-0043](0043-juju-page-guesses-nothing.md), and its
resolution of the model inside each command by
[ADR-0049](0049-juju-page-model-from-environment.md). The per-card model pins
stand.

## Context

[ADR-0037](0037-gallery-pages-site.md) generates the site's Gallery page from
the bundled manifest, and that page is deliberately provider-agnostic: every
input the entry leaves to the user renders as a placeholder, so
`atelier apply charmarr` reads
`--var model=<model> --var vpn_provider=<vpn_provider>`. That is the right
default — Atelier configures a module's declared variables and has no business
knowing what a provider means — but it is not a command anyone can paste.

Every module in the gallery deploys through the Juju provider, and the Juju
idioms are stable enough to encode once:

- **A model is always needed**, in one of three shapes the manifest does not
  reveal. `loki-operators` requires a UUID in `model_uuid`; `cos` and `cos-lite`
  take an object whose `uuid` selects an existing model; `charmarr` takes a
  model *name*. Emitting `model_uuid` everywhere is wrong for two of the three:
  for COS it warns `unknown variable ignored` and **still creates a new model**,
  which is the opposite of what the reader asked for.
- **`model_uuid` being optional is not a reason to omit it.** On
  `charmed-spark` it defaults to `null` and setting it is what *stops* the
  module creating its own model.
- **Credentials and channels have conventional defaults** (`$AWS_*` for the S3
  trio, `latest/stable` for a charm channel) that beat a placeholder.

A reader who has not installed Atelier has no way to learn any of this.

## Decision

Publish a second generated page, `/juju/`, whose commands are ready to run. It
sits beside the agnostic Gallery page rather than replacing it, so the site's
provider-neutral statement of what Atelier is survives intact.

- The knowledge lives in
  [`tools/gallerysite/juju.go`](../../tools/gallerysite/juju.go), **not** in
  `internal/gallery` and not in the manifest. The manifest keeps describing a
  module's inputs; the page adds what the Juju provider means by them. The
  binary and the CLI stay provider-agnostic, which is what
  [ADR-0016](0016-scope-boundaries-no-orchestration.md) and the layered package
  structure assume.
- The model UUID and name are read at run time from `juju show-model`, so one
  pasted command works for whichever model the reader has switched to. Both the
  command and the page state that `juju` and `jq` must be on `PATH`.
- The page never implies it runs unattended: an input with no safe default
  keeps its placeholder and the card lists what the reader still supplies.
- Where pinning the model changes a module's behaviour rather than filling a
  gap — `charmed-spark` stops creating its own model — the card says so.
- **The pins are gated.** `atelier gallery lint` checks the manifest's own
  `requires` against each module, so it cannot see a pin the generator invents.
  `just gallery-check` scaffolds each entry with its pin and asserts the
  variable reached the wrapper, which catches a module that drops or renames it.

## Alternatives considered

- **Teach `internal/gallery` about Juju.** Rejected: the manifest and the CLI
  would learn a provider, and every future provider would want the same special
  case. The site is where an opinion is affordable, because nothing depends on
  it.
- **Put the Juju inputs in `gallery.json`.** Rejected: the manifest describes
  module inputs, and a Juju-specific block would make every entry carry a
  provider section that only one page reads.
- **Emit `model_uuid` unconditionally, as one command shape.** Rejected: it is
  wrong for `cos`/`cos-lite` (creates a model anyway, with a warning) and for
  `charmarr` (wants a name, not a UUID).
- **Give the page committed, hand-written commands.** Rejected: the drift
  ADR-0039 rules out; a ref bump or a new entry would leave them stale.
- **Teach the CLI (`atelier gallery list --juju`).** Deferred, not rejected: it
  is the natural follow-on, but no user has asked for it, and
  "lean by default" says do not build it until someone does.
- **Add the pins to each entry's presets.** Rejected: a preset is a `.tfvars`
  bundle ([ADR-0031](0031-presets-as-tfvars-bundles.md)); it cannot carry a
  `$(juju show-model …)` substitution, since the value must be resolved by the
  shell before Terraform sees it.

## Consequences

- The site grows a second generated page and a second nav entry. Both are
  regenerated by `just site-build` and gitignored, so neither can drift.
- `tools/gallerysite` gains a Juju-shaped file. It stays a build-time tool with
  one consumer, which is what keeps the knowledge affordable.
- `just gallery-check` gains a scaffold assertion per pinned entry, so it
  depends on the generator agreeing with the manifest about which pins are
  optional.
- A module that stops taking a pinned model fails `just gallery-check` rather
  than publishing a command that quietly does nothing.
